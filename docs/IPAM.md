# IPAM source of truth and implementation

IPAM owns intended network and address configuration. DNS records, DHCP leases, reservations, discovery results, and external inventory are observations or explicitly owned integration objects. Reconciliation identifies disagreement without silently replacing intent.

## Implemented first slice

### Automatic DDI population

The cluster coordinator (or standalone server) populates IPAM at startup, every 30 seconds and on inventory reads. No import action is required. Configured DHCP scope masks define exact subnets; conventional IPv4 octet-aligned and IPv6 nibble-aligned reverse zones provide additional prefixes. Classless reverse delegations do not imply a guessed subnet. Ambiguous overlaps are not merged automatically. Discovery currently targets the default network view; other views retain explicit intent.

DHCP reservations, configured gateways and enabled authoritative A/AAAA/PTR records within known subnets produce source-labelled address records. Active DHCP leases remain expiring observations, including synchronized lease evidence, rather than permanent static assignments. DNS-only addresses without a known network are not assigned a guessed mask. Existing operator allocations and metadata take precedence. Discovery removes only its own stale address records and retains networks for history. Source collection or persistence failures leave the previous inventory intact; unchanged scans do not advance revision. Replicas receive coordinator inventory through the existing cluster configuration transfer.

Subnet inspection exposes dynamic DHCP pools and exclusions. Next Available excludes these ranges, configured gateways, allocations and observations using interval arithmetic rather than enumerating addresses. Saving an assignment still requires the current revision and uniqueness checks; a suggestion alone makes no reservation on a device or live DHCP allocator.

The module persists network views, IPv4 and IPv6 subnet and container prefixes, site and VLAN metadata, intended address assignments, and revisioned change history with before and after values. Independent network views allow overlapping private space. Subnets cannot overlap within a view unless a containing prefix is explicitly an organizational container. Containers cannot carry assignments or service links.

Assignments have hostname, owner, description, and Assigned, Reserved, or Deprecated state. Each address is unique within its view. Network and broadcast addresses are excluded for ordinary IPv4 subnets; /31 and /32 are supported. IPv6 capacity and address arithmetic use arbitrary precision, and available address suggestions do not enumerate large networks.

Explicit links connect a subnet to a local DHCP scope and DNS zone. Inspection combines current leases, reservations, and A/AAAA records with intended assignments, reporting unmanaged addresses, hostname drift, duplicate client lease evidence, and assignments without observations. Absence of DNS or DHCP evidence does not prove an address is free or a device is offline. DNS records do not prove a live connection.

Writes require an inventory revision and are serialized inside one process. Invalid or stale writes leave the previous state intact. File replacement follows a flushed temporary snapshot. Settings backups include `ipam.json`, and restore validates and loads that inventory. Cluster configuration transfer includes the same inventory, and API mutations are restricted to the existing cluster primary. Historical lab inventory convergence is bounded evidence; production inventory convergence, failover and enterprise storage availability are not established by these store/API checks.

The web console includes an IPAM tab for inventory, creation and editing of subnets and assignments, address suggestions, observations, utilization, and recent changes. APIs reuse Settings view, modify, and delete permissions. Reading linked DHCP or DNS observations additionally requires the corresponding existing source permissions. Dedicated per-view delegation remains future work.

## API contract

Use the existing authenticated API transport and bearer session token. Mutations use POST form data. The usual API status envelope contains results under `response`.

| Endpoint | Method | Parameters |
| --- | --- | --- |
| `/api/ipam/list` | GET or POST | None |
| `/api/ipam/views/set` | POST | `revision`, `name`, optional `id`, `description` |
| `/api/ipam/subnets/set` | POST | `revision`, `name`, `prefix`, optional `id`, `viewId` defaulting to `default`, `site`, `vlan`, `container`, `dhcpScope`, `dnsZone` |
| `/api/ipam/assignments/set` | POST | `revision`, `subnetId`, `address`, optional `id`, `hostName`, `owner`, `status`, `description` |
| `/api/ipam/delete` | POST | `revision`, `kind` equal to `view`, `subnet`, or `assignment`, and `id` |
| `/api/ipam/subnets/inspect` | GET or POST | `subnetId` |
| `/api/ipam/addresses/nextAvailable` | GET or POST | `subnetId` |

Available address responses are suggestions, not atomic live DHCP claims. IPAM Reserved state records intended reservation; it does not create a DHCP reservation. This slice does not prevent another provisioning system or a DHCP allocator from using an intended address. Automated provisioning requires a separate coordinated workflow with allocation holds, service validation, acknowledgement, and rollback.

## NetBox relationship

NetBox models prefixes in VRFs, distinguishes container prefixes, and represents interface IPs with masks and roles. Preserve these semantics rather than flattening inventory into DNS records. Source ownership must be selected before a live connector writes to NetBox or imports intent that can alter service configuration.

The selected current authority is teQtanium-owned IPAM exporting to NetBox. Individually reviewed missing-intent reverse proposals are available; remote authority modes remain unavailable. Across future modes, preserve stable external object IDs, source revision, last applied values, and provenance. Conflict detection must precede synchronization. Retry using idempotent operations and never resolve disagreement by blindly applying the most recent timestamp.

The implemented connector publishes DDI-owned prefixes and address intent through NetBox's REST API. An operator explicitly maps each network view to an existing VRF ID, or to the global table; two views cannot map to the same VRF. Prefix containers, address masks, DNS names and address status are preserved. Preview records creates, updates, unchanged objects and conflicts without writes. The console shows desired addresses and before/after field changes. Objects without this installation's provenance marker are conflicts, including an existing address with a different mask; they are never silently adopted or deleted.

Configure publication in the IPAM console with an HTTPS URL, `DDI_NETBOX_*_API_KEY` environment reference, Bearer v2 or legacy Token authentication, and view/VRF mappings. NetBox settings and publication require Administration and Settings modify permissions and run on the cluster primary. No secret is stored in policy. Requests reject redirects and pagination outside the configured API origin, with bounds of 100 pages, 10000 objects and 8 MiB per response.

Apply uses a preview ID bound to local inventory revision and settings, expiring after fifteen minutes. Updates require matching remote timestamps/provenance and ETag/If-Match support. Creates recheck natural identity before submission. A submitted preview is not automatically replayed after an uncertain HTTP outcome; a new preview reconciles remote state. Partial writes are recorded, and external changes are not globally transactional. NetBox may allow concurrent duplicate creates when another writer does not enforce uniqueness; local canonical-origin admission serializes supported connectors sharing a host/temp namespace, while external concurrent writers and distributed uniqueness remain unqualified. Backup includes the integration settings and installation provenance, but excludes the key.

The API provides `/api/ipam/netbox/settings/get`, POST `/settings/set`, POST `/preview` and POST `/apply`. Mock tests cover provenance, conditional updates, stale intent, conflicting objects, credential/transport restrictions, lost responses and backup identity. Production NetBox HTTPS authentication and conditional-write behavior have been tested; application publication remains disabled pending activation. Scheduled reviews, individually selected managed deletions, missing-only manual reverse proposals, and explicit existing site/VLAN/tenant/device/interface references are implemented within the [local reconciliation review contract](NETBOX-RECONCILIATION.md). Scheduling never publishes automatically; remote authority, DCIM creation, relationship unlinking and custom-field ownership remain unavailable.

For an operator-approved migration, back up both inventories and the NetBox database before explicitly establishing per-object ownership. A provenance marker must occupy its own line; multiple owners are rejected. Existing notes alongside a single ownership marker are preserved during previews and updates. The connector still does not adopt objects automatically. Dynamic DHCP observations must not be converted into fixed assignments merely because they appear in an external inventory.

REST/authentication and conditional-write references: [NetBox REST API](https://netbox.readthedocs.io/en/stable/integrations/rest-api/), [IP address semantics](https://netbox.readthedocs.io/en/stable/models/ipam/ipaddress/), and [prefix semantics](https://netbox.readthedocs.io/en/stable/models/ipam/prefix/).

Sources: [NetBox prefixes](https://netboxlabs.com/docs/netbox/models/ipam/prefix/), [NetBox VRFs](https://netboxlabs.com/docs/netbox/models/ipam/vrf/), and [NetBox addresses](https://netboxlabs.com/docs/netbox/models/ipam/ipaddress/).

The lab uses unique temporary configuration, loopback listeners on high ports, and disabled default DHCP service. It does not test remote access paths or live network deployment.

## Reviewed local host provisioning

The console's **Provision a host** disclosure provides preview, explicit approval, apply, saved results and recovery. This bounded implementation supports one selected IPv4 address in the default view, linked to a local unsigned primary DNS zone with dynamic updates denied and a local unshared DHCP scope with DHCP DNS updates disabled. It creates an A record with a 300-second TTL and a reservation for an explicitly entered Ethernet hardware address. It does not create PTR records or enable a scope. Disabled scopes can receive saved reservation configuration; the screen identifies them as disabled and does not claim client service. Remote destinations, clusters, distributed ownership plans, pending ownership preparation, overlapping local scopes, signed zones, delegated names and DHCP-driven DNS side effects are refused before submission. IPv6 provisioning is not implemented.

Preview records immutable explicit intent and current service preconditions without writing DNS or DHCP. Approval binds the request digest, actor, inventory revision and ten-minute review lifetime. Approval drains the selected scope's supported native serving/admin requests outside the inventory lock, rechecks conflicts, then atomically persists a unique address hold. The native allocator consults holds by exact scope and address; neither approval nor a hold creates a synthetic lease, offer or observed address. Existing leases, offers, quarantine, exclusions, infrastructure addresses and another reservation cannot be adopted as a new request, including for the same client. Competing IPAM writes cannot replace a held address or its network links. Discovery continues to expose native observations in inspection, but pending transaction effects are not imported as static inventory.

The journal resides in `ipam.json` and is included in existing inventory backups. Each service submission follows a flushed, atomically replaced journal transition. DNS uses an operation-marked conditional RRset mutation, synchronous file persistence and file-byte readback; DHCP uses a conditional per-client reservation mutation and parsed scope-file readback with errors surfaced to the caller. Neither path replaces a reservation collection or restores an old service snapshot. The final intended assignment is saved only after both configuration acknowledgements. Results describe configuration acknowledgements at their recorded time, not continuous health or a promise that a client obtained a lease.

A lost or failed acknowledgement retains the address claim as **Reconciliation needed**. Reconcile the same operation reference; do not create a substitute request. Restart loads the journal and restores allocator hold checks before native serving. It does not automatically replay service writes. Reconciliation checks operation markers and current destination state before retrying. Recovery removes only this operation's unchanged record and reservation and persists the result. An external edit, active client lease, unavailable authority or unconfirmed compensation retains the claim for operator review. Recovery requires native DNS/DHCP delete permissions as well as Settings modify permission. Cancellation releases only an unsubmitted Preview or Approved request.

Native API routes are under `/api/ipam/provisioning/`: `preview`, `approve`, `apply`, `cancel`, `result` and `list`. Mutations are POST-only. Preview takes the current inventory revision, a new 32-character GUID operation ID, subnet, address, full host name, hyphen-separated hardware address and optional owner. Approval and apply use the recorded operation ID and digest. `apply` with `recover=true` requests conditional compensation. Results/list expose only the requesting actor's operations with applicable current native view permissions. Cached same-ID previews, repeat approval and cancellation also require current view and modify access to the operation's original DHCP/DNS destinations before returning stored data or changing its hold. Recovery requires current view, modify and delete access before changing the journal. Effective grants can come from separate existing user/group permissions; no new grant is created by retrying. Revoked access denies the request and retains its hold; restoring the required rights allows the original operation ID to be reconciled. Settings permission alone does not authorize these mutations or cached mutation responses. Historical result reads remain available after cluster initialization; new provisioning mutations remain unsupported there.

The local-file revision/write lock rejects stale competing inventory instances before persistence, and an operation file lock prevents overlapping execution of one ID across cooperating instances. This is not a shared-storage or cross-node transaction protocol. One supported native service owns each configuration directory; arbitrary external file writers and old binaries do not participate in these checks. Local process restart, native packet-handler offer/ACK, loopback DNS UDP and actual served desktop/390-pixel UI are qualified in private test evidence. No production deployment, OS DHCP client/relay network, port 67/68 wire path, abrupt process kill at every boundary, remote filesystem durability, exhaustive zone-delete race, or enterprise-wide transaction acceptance follows from those fixtures. Independent review and separately authorized deployment qualification remain required.

### Browser session privacy

Signing out, session invalidation and a new actor/session clear the selected provisioning request, draft form, feedback and actor history. Responses from the retired browser session cannot repopulate those views or expire a newer session. This clears presentation state only: it does not cancel a submitted operation, release a native hold or undo service configuration. After signing in, reload your authorized request history to reconcile an operation under its existing reference.


## Bounded active discovery

Active discovery adds read-only observations separately from operator intent, native DNS/DHCP configuration, leases and transaction holds. Configure sources under **IPAM → Active discovery**. Current effective Settings and Administration **View** permissions are required for source status/results. Configuration, qualification, manual collection and cancellation additionally require both **Modify** permissions. Removal requires both **Delete** permissions. Effective grants may compose across users and groups. Current permissions are checked again after network I/O; revoked access does not receive a saved result. Ordinary Settings inventory excludes collector configuration, results and private source history. The existing inventory backup/migration administrators retain their explicit whole-configuration access.

This first implementation supports standalone collection only. Cluster mutation is refused until coordinated source ownership is implemented. It does not install schedules, start collectors on inventory reads, run on service startup, or infer approval from existing DNS/DHCP records. There are no default targets or cloud accounts. New sources are disabled. Record an approval reference covering the exact target scope, save, and explicitly **Qualify approved scope**. Enable manual collection only after a complete successful qualification under unchanged configuration within its freshness window. Enablement alone sends no requests. Changing configuration saves it disabled and clears that source's former configuration evidence/qualification; review scope before recollecting. Editing or removing an in-flight source is refused: cancel and wait for its final outcome first.

| Collector | Explicit scope and evidence | Limits and meaning |
| --- | --- | --- |
| TCP connection | 1–64 unique literal unicast IPs within the selected subnet; one selected TCP port | Four concurrent connections; no CIDR expansion, hostname resolution, service commands, reverse lookup or application payload. Accepted connection is **ConnectionConfirmed**: listener acceptance at collection time, with service health and device identity unverified. Connection refusal produces no positive row; timeout/unreachable/error fails the snapshot. |
| SNMP device and ARP | One literal management IP and UDP port; SNMPv2c read community from a `DDI_DISCOVERY_*` environment reference. Reads sysName (`1.3.6.1.2.1.1.5.0`) and walks ipNetToMediaPhysAddress (`1.3.6.1.2.1.4.22.1.2`) using GET/GETNEXT | Only selected-subnet rows are retained. The configured row bound counts all traversed table rows, including those outside the subnet; device identity also counts toward the result bound. Version/community/request ID, advancing OIDs and response structure are checked; response ≤8 KiB. **DeviceReported** describes the device reply and ARP cache, whose entry age and endpoint reachability are unknown. No SNMP SET. SNMPv2c has no transport encryption; use only an approved management path. SNMPv3, IPv6 neighbor tables, SSH/vendor commands and LLDP are not implemented. |
| Azure NIC inventory | One explicitly selected subscription UUID and resource group at `https://management.azure.com`; bearer environment reference with a token for that management audience and minimal `Microsoft.Network/networkInterfaces/read` rights | API version `2024-07-01`, GET only, fixed origin/path, TLS validation, no proxy or redirects; pagination must stay in the exact subscription/group NIC-list path. At most 10 pages, 1 MiB/page, 4 MiB/run, configured object/address bound; duplicates, malformed/missing inventory and foreign object IDs fail. **ProviderReported** means NIC private-IP configuration, not live endpoint connectivity. No provider event timestamp is invented. Resource groups/regions are not enumerated; public IP expansion, other clouds, managed identity login/token acquisition and automatic token refresh are unimplemented. |

Every source selects an existing leaf subnet and therefore its explicit network view. Overlapping views and multiple sources retain separate identities. Source configuration stores environment variable names only; secret values are read at execution and never persisted or returned. The operator supplies approved credentials in the server environment outside this API. This is a scope record and access check, not independent validation that an approval reference is authentic or that the external credential has minimal privileges.

Each source supports 1–256 results/table rows, 100–5000 ms per request and 60–86400 seconds of freshness. There are at most 32 sources and one active run per manager/service instance, with no queue. Each run stops after 30 seconds, operator cancellation or request abortion. Network I/O runs outside the inventory lock. Cooperating inventory writes retain existing revision/file-lock checks; the run gate is not a cross-process scheduler or shared-storage ownership protocol.

Source state persists last attempt, last complete collection, actor, typed outcome reason, explicit truncation flag and bounded last-known evidence in `ipam.json` through the existing flushed atomic snapshot replacement. A Running attempt is persisted before I/O. Restart retires it as Interrupted and retains prior evidence, without replay. Inventory restore is refused while a collector is active; an in-flight attempt contained in a restored snapshot is retired without replay. Failed, timed-out, malformed, over-limit, cancelled or partially completed transport never replaces the last complete snapshot or refreshes old observation timestamps. A complete explicit empty result is different from a failed/missing response. On a complete run, rows absent from the latest result remain marked missing (within the configured retained-row bound), with their original timestamp; current rows take priority if the bounded history is full. A source edit/removal discards only its own configuration evidence. Disabling prevents ordinary collection but retains previously collected evidence until its recorded expiry; explicit qualification remains possible.

Observation time is the local collection time, with a separate local last-attempt/last-complete timestamp and expiry. Confidence is a reasoned type, without a fabricated percentage or claim of endpoint liveness. Future local timestamps beyond five minutes and expiry beyond the source freshness policy are rejected on load/restore. Provider/ARP event times are unavailable in this slice. A source can be failing while its last-known observations remain within their expiry; the screen shows both source health and evidence age. Reload sources to update time-based freshness presentation.

Current, present observations participate in subnet inspection and unmanaged/hostname/hardware-conflict findings. Next Available conservatively excludes them even for a reader who cannot view private source detail. Current active occupancy rejects supported provisioning preview/precondition checks; arriving observations cannot release an existing hold or grant authority. Expired/missing rows remain available to authorized source readers but no longer count as current occupancy. Neither expiry, an empty result nor a failed probe proves an address is free. Allocations, exclusions, native leases/offers/quarantine and transaction holds keep their existing independent protections. Discovery does not install enforcement into the DHCP allocator or make an arbitrary manual assignment save into an atomic device claim.

API routes use the existing authenticated envelope: GET/POST `/api/ipam/discovery/status`; POST `/sources/set` (`revision`, camel-case JSON `source`), `/sources/delete` (`revision`, `sourceId`), `/run` (`sourceId`, optional `qualify=true`), `/cancel` (`sourceId`) under that discovery prefix. Status reports source configuration, runs, active IDs and current action permissions. Cancellation acknowledges a request; reload status for the persisted final outcome. A run returns a source outcome, not success merely because the HTTP request was accepted. Administrative peers with the same existing source permissions share source results; this slice does not introduce per-source actor delegation.

Qualification: `dotnet run --project tests/Ipam.Tests/Ipam.Tests.csproj -c Release -- --discovery` uses actual isolated native HTTP, TCP, UDP SNMP and TLS Azure-shaped fixtures. The Azure test adapter rewrites the fixed logical Azure origin to a pinned ephemeral loopback TLS server; it proves transport/parser/scope contracts, not actual Azure authentication or inventory. Native fixtures cover current effective permissions, role revocation during I/O, explicit cancellation/client abortion, bounds, partial/stale/missing evidence, actual persistence failure, restart, unmanaged conflicts and preservation of native provisioning holds. Production SNMP community access, remote management paths, cloud account/audience/RBAC, real provider pagination and live discovery remain unqualified. No production collector is enabled by this change. Private readiness evidence found four historical approved read-only switch targets and no cloud vault candidates; those findings do not establish new protocol activation approval or cloud authority.


### Parent scope and interrupted persistence

A qualification now binds the source configuration to its parent subnet ID, canonical prefix, network-view ID and container status. Remove all linked discovery sources before changing that parent scope or deleting the subnet; then configure and qualify sources for the new scope. The same rule applies to idle and active sources and to inventory restore. Ordinary subnet metadata can still be edited. Legacy qualifications that recorded only the subnet ID are disabled and marked for scope review on load/restore. Their old evidence and timestamps remain available as historical source results, but cannot drive current occupancy, inspection, suggestions or enablement in an unverified context. Explicit qualification starts a fresh snapshot under the current parent context.

If collection stops but the terminal snapshot cannot be saved, the service retains the real pending job and its admission claim. Status shows **Saving outcome** and explains that storage must be restored. Reload sources, request cancellation, or retry collection to retry the pending save; these actions never repeat the collector transport until that outcome is durable. A successful retry removes the active ID and exposes the saved terminal result. Restart retires the persisted in-flight marker as Interrupted without replay. An obsolete instance still fails the existing revision/file-lock check. This is a bounded single-service lifecycle repair, not cross-process or shared-storage job ownership.
