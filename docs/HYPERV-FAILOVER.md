# Historical Hyper-V fenced failover boundaries

`scripts/hyperv-ddi-controller.py` and `scripts/fence-hyperv-ddi.ps1` implement an opt-in isolated-lab path. They require pinned VM identities, SSH host keys, HTTPS certificates, an authorized management source and the donor's recoverable authoritative disk. This is distinct from the VMware unused-capacity controller; historical Hyper-V success does not qualify current production recovery.

The lab workflow investigates consecutive management failures, verifies every donor adapter's persistent fence, reads original durable authority under the fence, surrenders bounded idempotent address batches with lease/offer/quarantine protection, imports complete grants and promotes the survivor. It retains the former owner's fenced identity. Authentication/certificate failures and stale replicas cannot establish reusable capacity. The recovery API relies on an authorized administrator's physical-fencing attestation; it does not verify a cryptographic fencing receipt.

The controller supports at most 65,536 owned addresses per scope and a single host writer. It has no automatic unfencing, grant return, failback/rejoin, redundant controller or destroyed-disk recovery. A logon task depends on its host and user session. A two-guest, single-host lab cannot establish host-failure or regional availability.

The [historical retest](AUTOMATIC-FAILOVER-TEST.md) reported bounded service-failure/VM-power-loss takeover, existing-lease renewal and promotion after a Linux directory-durability repair. It does not establish exhaustive crash points, Windows/macOS power durability, all authorized access paths, actual production client/relay paths or current loaded-runtime behavior. [Current recovery](DEPLOYMENT-STATUS.md) remains incomplete and Disabled; the accepted local quarantine is undeployed.

Deployment-specific identities, inventory, task configuration, credentials and receipts must remain private. Any separately authorized fence/ACL/credential operation must retain the original administrative sessions until separate fresh sessions from every required affected source prove authentication, privileges and target-seen source. Verify intended recovery outcomes separately and report untested paths. No instruction here authorizes installation, restart, fencing or recovery enablement.
