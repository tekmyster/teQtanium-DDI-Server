# Backup and new-deployment migration

Open Settings > General. Backup Settings preserves selected configuration, identity and operational data for recovery. New Deployment creates a portable package for a fresh standalone destination.

## Move to a new deployment

1. On the source, choose New Deployment > Download Package. Store the ZIP securely: DNS keys and client lease data can be included.
2. Install and sign in to a fresh standalone destination using its intended credentials and management addresses.
3. Open New Deployment, select the package and choose Preview Import. Review zone/scope counts, portable DNS settings, inventory, security policy and checksum status.
4. Choose Import Package. DHCP scopes stay disabled. Test DNS records, settings, security and a separate fresh administrative login before any live cutover.
5. Review authoritative NS/SOA records, secondary-zone upstreams, destination interfaces and external integration settings. Transfer distributed DHCP authority or stop/fence the former standalone owners before activating client service. Join the intended cluster separately.

Packages include current DNS zones/keys, resolver/cache/filtering settings, DHCP options/reservations/lease snapshots, IPAM intent and security policy. Current runtime zones/scopes include edits awaiting delayed saves. Cluster catalog identity is omitted; imported members are detached from the former cluster catalog. Zone authority types and upstream settings are retained. Imported policy uses Protection Monitor, DNS Monitor and DHCP Observe. External MISP/model/feed configuration is cleared and remains disabled; configure enrichment separately on the destination. Applications, TSIG trust, management configuration, external integration credentials, event/enrichment history and allocation journals use separate backups or explicit setup.

The destination keeps its credentials, management ports/certificates, server identity, DNS listening/source addresses, optional protocol listeners and cluster identity. Copied leases do not surrender source allocation authority. An active source must not share those pools with the destination merely because a snapshot was imported.

## Review and recovery

Migration requires an interactive administrator with Settings and Administration deletion privileges. Cluster service tokens cannot invoke it. The destination must be outside a cluster, have no user zones or configured scopes, no active scopes/leases and no distributed allocation plans. An unused disabled Default scope is permitted. Stop other configuration work during migration; the destination fingerprint is checked immediately before applying the review. Independent APIs are not covered by a global configuration transaction.

Reviews belong to the reviewing administrator, expire after ten minutes and are consumed on import. A new review replaces that administrator's previous one. At most four packages are held. Two previews can parse at once. ZIP uploads are limited to 16 MiB (plus 40 bytes for the encrypted envelope), 2,048 entries and 128 MiB expanded total; each expanded file is limited to 16 MiB. Unsafe/duplicate paths and checksum mismatches are rejected. Checksums detect changes; they do not authenticate the sender or encrypt the ZIP.

Existing Technitium backups can supply zones, scopes and filtering files. They have no migration checksum manifest and retain destination resolver settings when portable settings are absent. Archives containing node-specific DNS settings, authentication, cluster, syslog or allocation state must use the existing selective restore controls or a new-deployment export; the portable importer rejects them. Old cluster catalog archives require a new-deployment export. Unsupported data is not converted into authority.

Before applying changes, the service flushes an authority-free write-ahead preimage (`migration-pending.zip`) and an actor-bound operation receipt (`migration-operation.json`). The receipt binds the review/operation identifier, exact decrypted package SHA-256, source snapshot, destination fingerprint and initiating administrator. A separate `migration-before-<identifier>.zip` retains the same selected recovery data. These local preimages are plaintext and can contain DNS keys and existing destination policy: they inherit the destination configuration folder's protection boundary. Provision that folder securely and retain/remove recovery ZIPs explicitly after validation. This change does not provision keys or change host ACLs.

A caught failure restores the selected native settings and data. A process interruption before commit triggers idempotent preimage rollback **before managers load or listeners start** on the next launch. The same operation then reports `RolledBackAfterInterruption`; a fresh authorized preview is required to apply the package again. This is restart-safe rollback and authorized retry, not unattended continuation of an expired browser session. A damaged checkpoint blocks startup of that staging destination pending operator recovery. The original source is never stopped by this workflow.

After all component writes and disabled-scope checks, the DNS configuration is flushed and the operation receipt is atomically marked `Committed` before removing the pending marker or acknowledging the client. A lost reply can be reconciled with `POST /api/settings/migration/status` (`operation=<review>`). Repeating import with that same identifier returns the existing committed receipt without applying again. Receipt lookup requires the same actor and current interactive administrative privileges. The retained receipt covers the latest operation only; old identifiers require a new preview and must still pass the unused-destination rules. A committed receipt describes a historical apply; query current records/settings before cutover.

Checkpoint restoration writes only its exact validated configuration namespace. It never restores allocation plans, grants, owner journals, cluster membership/identity, credentials, trust anchors or syslog spool. Each checkpoint entry is verified before mutation; interrupted rollback is idempotent. Reparse points are refused. Component writes are atomic file replacements with flush and directory synchronization where supported; multi-component visibility and other administrative APIs are not a global transaction. Freeze other configuration work during import. Native process termination testing does not establish host power-loss or storage-hardware durability.

## Scheduled encrypted portable backups (API)

The console remains unchanged. The following **POST-only** per-node API workflow requires a current direct interactive administrator with Settings View/Delete and Administration Delete rights. It is a portable configuration backup workflow, not full machine recovery or online cluster replacement.

1. `/api/settings/backups/configure`: body `enabled=true`, `intervalHours=1..168`, `retain=1..30`. Scheduling defaults to disabled and persists in `backup-schedule.json` without a secret.
2. `/api/settings/backups/unlock`: body `encryptionKey=<Base64 of 32 cryptographically random bytes>`. Supply the same key to recover historical artifacts. Never put it in a URL. The service copies the decoded key into memory only and delegates the fixed portable-backup scope to that current interactive session. Logout, expiry, disabled user or lost privileges prevent capture/commit and clear the delegation when checked. Restart always locks the key. `/lock` explicitly clears it. Keep the key in an independently managed secret store; losing it makes its backups unavailable. Passphrase derivation and persistent key-store integration are not implemented.
3. The background timer wakes every second and actually captures the first due job after enable/unlock. UTC interval semantics apply: one job at the next wake, then `now + interval`; missed intervals coalesce, with no catch-up queue. DST has no effect. Forward wall-clock jumps admit at most one job; backward jumps delay the stored in-memory deadline. Restart/unlock starts a new interval epoch. The persisted schedule survives; deadlines and counters are per process. A locked due run is skipped visibly without plaintext fallback.
4. `/status` reports enabled/locked state, next UTC deadline, current-process success/failure/coalescing/locked counters, committed filenames and interrupted staging filenames. `/run` intentionally starts a separate manual job. Concurrent manual jobs are rejected; due ticks coalesce. Schedule/key/lock/download changes serialize with the active job and acknowledge only after it finishes; disabling is not cancellation of a job already in progress. A configuration/import gate wait is limited to ten seconds. Backup failures are isolated from the DNS/DHCP transaction paths.
5. `/download`: body `artifact=<exact filename>` returns the encrypted artifact. `/run` and status distinguish authenticated archive readback from native restoration verification. No job claims that DNS restoration succeeded merely because the archive was committed.
6. Upload that `.tqb` file to `/api/settings/migration/preview` as multipart field `file`, with multipart `encryptionKey`. Decrypt/authenticate, parse/check the archive, then use the returned actor-bound review with `/migration/import`. The existing ZIP console accepts plaintext packages; it has no encryption-key or schedule controls in this bounded API delivery.

The `TQB1` envelope uses the platform .NET `AesGcm` implementation with a 256-bit key, random 96-bit nonce, 128-bit tag and a 24-byte authenticated header: ASCII magic/version (4), nonce (12), little-endian plaintext length (8), followed by ciphertext and tag. There is no password flag, KDF, salt or embedded key. Format, nonce and length are authenticated; the encrypted plaintext contains the package schema, unique artifact identity, source name, capture UTC, declared scope and per-file SHA-256 manifest. GCM authenticates possession of the key, not an independently certified source identity. The key must come from a trusted channel. Plaintext is at most 16 MiB, ciphertext overhead is exactly 40 bytes. Wrong key, tamper, missing tag, version mismatch and size violations fail before import mutation.

Snapshots include runtime zone/key and scope edits and portable DNS values, plus separately locked IPAM and stripped policy snapshots. Each component is coherent under its own engine contract; concurrent edits across components are not an application-wide consistent point in time. Filtering files retain the native disk-save semantics. Pause administrative writes if a coordinated snapshot is required. A backup is committed by encrypted temporary-file flush and rename, then freshly read, authenticated, checksum/schema validated before retention. No plaintext schedule artifact is written. Decrypted previews remain in bounded memory for at most the review lifetime (expired reviews are cleared on the timer); managed request strings/temporary copies cannot be guaranteed physically erased.

Retention targets only exact store-owned `backup-<32 hex>.tqb` filenames, after a new artifact passes readback. It removes oldest excess artifacts only when the current key can authenticate/validate them; unrelated, corrupt or retired-key files remain for operator review. At most 31 complete 16-MiB artifacts (30 retained plus a newly committed candidate) and one active encrypted temporary file can arise under the owned namespace; a count beyond 30 blocks another capture. More than 64 directory entries blocks work for explicit review. This bounds normal store-owned data to about 512 MiB including active staging; unrelated files require operator management. Old-key archives are deliberately not silently deleted. Count retention is not age retention, off-site replication or native-restoration certification. Rotating keys means retaining all historical recovery keys externally.

A process stopped after encrypted staging is flushed leaves an identifiable `.pending-<identifier>` file. It is excluded from completed-artifact status. Startup stays locked; the next freshly authorized unlocked job removes only exact store-owned orphan staging and starts a new artifact with a new random nonce. It does not claim the interrupted job completed. Filesystem write/full failures retain existing files; a failure after a committed rename can leave an unverified candidate requiring review. Retention never treats a truncated candidate as a verified replacement. Native power-loss durability, Linux filesystem behavior and network filesystems require separate qualification.

## Coverage and authority boundaries

| Data | Scheduled portable backup / standalone import | Same-node selective native restore | Online replacement |
| --- | --- | --- | --- |
| DNS zones and embedded keys | Included; runtime zone snapshot; authenticated/encrypted at rest; native record and DNS readback tested | Existing explicit selections; native ZIP is plaintext | No cutover workflow delivered |
| Portable resolver/filter settings | Included; retain destination listeners/interfaces and identity; filters use native saved files | Existing explicit DNS settings selection may include deployment-specific state | Unqualified |
| IPAM intent and policy | Included; Protection Monitor/DNS Monitor/DHCP Observe; external MISP/model/feed references cleared | Existing native selections retain their separate behavior | Unqualified |
| DHCP scope options/reservations/lease observations | Included snapshot; all imported scopes disabled; leases are observations and never ownership proof | Separate native scope-restore safeguards; not expanded by this change | No allocation/takeover or membership action |
| Management credentials/auth/ACLs, server/cluster identity and certificates | Excluded; destination retained; newly loaded zones receive existing native administrative permission setup | Explicit native restore choices can change these and require fresh-session validation | Unqualified |
| Per-node syslog settings/CA/spool/history | Excluded; destination configuration and CA remain untouched; no replay | Existing accepted CA Retain/fresh revision semantics, no spool/history | Unqualified |
| External connection credentials, apps, logs/history, enrichment cache | Excluded; historical rollback audit/history artifacts are not erased | Separate explicit native selections | Unqualified |
| Allocation plans/journals, permanent grants, epochs, fences, voting/membership authority | Excluded from portable archive and preimage; unsupported input rejected; existing local bytes never replaced by this path | Existing broader native restore is not newly qualified for authority recovery | **Blocked**: no fresh cooperative quorum/current-authority protocol or safe cutover proved |

All three modes require deployment-specific recovery planning. Only the API portable backup/standalone import/restart rollback scope is implemented here. Same-node whole-system recovery, a real online cluster replacement, live DHCP packet availability/takeover, disk-loss recovery and production activation remain separate gates. Recovery automation remains Disabled.

For ordinary restores affecting authentication, management ACLs or credentials, keep the original administrative session until a separate fresh session from each required source proves login and required privileges. Existing sessions and reachable ports are insufficient.

## Verification

The dedicated migration suite now checks: native export/preview/import, manifest tampering, unsafe paths, anonymous rejection, stale runtime previews, legacy backups, failed-import rollback, retained identity/listeners, disabled scopes, exact lease identity/expiration snapshots, DNS records, IPAM/security policy, catalog detachment and fresh administrative modification. The console was inspected at desktop and 390-pixel widths. Browser import confirmed named controls, initial dialog focus, readable previews, success feedback, refreshed settings and disabled replay controls. Full ZIP export responses passed API checks. The in-app browser did not expose Blob download completion through its automation event, so filesystem download completion was not verified through that browser.

Backup-recovery native verification uses a new owned benign fixture and full native child processes. It covers an actual due scheduled encrypted artifact, standard AES-256-GCM known-answer vector, wrong-key/tamper/truncation/size/path/authority negatives, retention/concurrency, current authorization across capture, interrupted encrypted staging, pre-apply/mid-component/committed-before-reply process kills, fresh authenticated reattachment and semantic settings/record/DNS readback. Exact final counts, executable identities, timings, failed intermediate receipts and limitations are in the immutable handoff. The earlier console verification above is historical; this change leaves every static asset byte identical and makes no new browser claim.
