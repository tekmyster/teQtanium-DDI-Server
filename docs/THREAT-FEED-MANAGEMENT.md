# Typed feed management and the exact QNAME RPZ fragment

This API-only change extends the existing typed EDL input cache. Imported evidence, local manual rules, explicit EDL publication selections and publication intent remain separate. Monitor, DNS Monitor and DHCP Observe remain the defaults. No production activation, publication, deployment or detection-accuracy claim is part of this change.

## Source and quality contract

`SecurityPolicy.EdlFeeds` retains the existing maximum of eight HTTPS sources. `Kind` is `Domain`, `Network` or `Url`. `Format` defaults to `Plain`; `RpzQnameNxdomain` requires `Kind=Domain` and a normalized lower-case `RpzZone` without a final dot. Endpoints retain existing restrictions: no URL credentials, query or fragment; HTTP 200 and `text/plain` only; no redirect following in the native client; strict UTF-8; 2 MiB, 20,000 lines and 10,000 distinct entries per response. The complete multi-source cache remains bounded at 16 MiB. Failure of any record rejects that source's complete response.

`SourceConfidence` defaults to 50 and accepts 0..100. It is an operator assessment, never measured accuracy or a maliciousness probability. It replaces the previous inference of confidence 100 from a Block action; explicit Block policy still uses the existing engine behavior. `MinimumConfidence` defaults to 0; equality is eligible. `Provenance` is an operator-supplied description of at most 512 non-control characters; its default explicitly says accuracy is unverified. Fetched provenance is retained separately from the current configured description in indicator evidence.

`MaximumAgeHours` defaults to 168 and accepts 1..168. Eligibility ends at the earliest of the original snapshot expiry, fetched time plus the current cache lifetime, and fetched time plus the current maximum age. Equality at expiry is inactive. Age measures local fetch age, not the original publisher's observation time. No remote confidence, freshness, provenance verification or source signature is inferred from plain/RPZ text.

New snapshots record UTC fetch/validation times, feed ID, type, exact source URL, format, RPZ origin, source-configuration digest, canonical values, content digest and generation. Source configuration binds ID/type/URL/format/origin/auth scheme/credential environment reference, without storing credentials. Changing those fields deactivates the old snapshot. Quality thresholds and action changes re-evaluate retained matching evidence. Disabling/deleting a feed or disabling the policy deactivates imported evidence. Other feeds and local manual rules remain independent.

Health separates active `entries` from `retainedEntries`, exposes `snapshotGeneration`, effective expiry, validation time and `integrityState`. Old cache files remain readable with `Plain` defaults. Legacy snapshots without a digest are explicitly `LegacyUnchecked`; they receive no invented validation timestamp or provenance. Refresh upgrades them to the new metadata. Existing policy files receive the new quality defaults. Malformed/digest-mismatched cold caches are rejected; DNS service and independent rules continue without that cache.

## RPZ fragment grammar and behavior

This is a record-fragment interchange subset, not a complete RPZ implementation or a general DNS master-file reader. The source syntax follows the exact QNAME and `CNAME .` NXDOMAIN notation described in the [RPZ Internet-Draft, sections 3.1 and 4.2](https://datatracker.ietf.org/doc/html/draft-ietf-dnsop-dns-rpz). That archived draft is a format reference, not a claim of IETF standard compliance.

An explicit `$ORIGIN configured.zone.` must precede records. Repeating that exact origin is allowed; changing it is rejected. `$TTL unsigned-integer` is accepted. Each record has an explicit owner, optional single unsigned numeric TTL and optional single `IN` class in either order, then `CNAME .`. Type/class/origin comparisons are case-insensitive; directive keywords use uppercase `$ORIGIN` and `$TTL`. Relative owners represent exact QNAMEs; absolute owners must end in `.configured.zone.` and that suffix is removed. Names canonicalize to the existing DNS normalization. Duplicate canonical names collapse into one sorted entry. Semicolon comments and blank lines are allowed. TTL fields do not override configured cache age.

For example:

```text
$ORIGIN policy.test.
$TTL 60
one.fixture.test IN CNAME .
two.fixture.test.policy.test. 60 IN CNAME .
```

Both names import as exact Domain evidence. Subdomains do not match implicitly. Source NXDOMAIN notation does not override the configured local action: default Monitor preserves answers; an explicitly configured Block uses the existing native REFUSED response. This change does not add a native NXDOMAIN response engine.

Unsupported input rejects the entire source response: wildcard/suffix rules, owner inheritance, escaped names, `@`, labels beginning `rpz-`, IP/client/response/NS triggers, passthrough, exceptions, NODATA, drop, TCP-only, local-data/redirect actions, SOA/NS/DNSSEC wrappers, parentheses, TTL unit suffixes, other classes and directives, includes, transfers and RPZ precedence rules. A full zone must be converted externally to the declared fragment before import. An origin-only/comment-only fragment with the required origin deliberately commits an empty snapshot; a comment-only fragment without origin is refused. An empty/comment-only Plain list deliberately commits an empty snapshot.

The existing authenticated direct-TLS EDL export accepts `format=rpz&zone=policy.test`. It uses the same immutable `EdlOutput` read for body and metadata. Only an explicitly enabled Domain publication with Block intent can export the fragment; Monitor intent cannot become NXDOMAIN implicitly. The explicit selected source/indicator IDs, exemptions, expiry and compatibility checks remain in force. Export does not enable a publication or change local DNS action. Consumers must provide their own complete zone wrappers; no SOA/serial/AXFR/IXFR capability is claimed.

## Scheduling and attempts

The native security worker polls every 250 ms and starts due enabled sources only while the security policy is enabled. First run is immediately due. Due times and attempts are local to the node/configuration root; one process-wide feed semaphore prevents overlap across all feed sources. Multiple processes sharing one configuration root and multi-node distributed exclusion are unsupported.

Sources are traversed in configured order. A failure does not prevent the next source from running; a slow source may delay later sources by its maximum 60-second whole-refresh deadline. No parallel-per-source fairness claim is made. Each source receives its own durable due time, failure count and attempt ID before network I/O. Backoff is `min(86400, RefreshSeconds * 2^(failures-1))`; the count caps at 16. Successful completion resets it and schedules from completion time. Cancellation/interruption conservatively retains the reserved backoff. Unrelated policy edits do not reset a matching schedule. An edit to the full feed definition starts a new configuration schedule. UTC absolute due times survive restart; a backwards clock shift delays work until due, and a forward shift makes work due. Invalid/out-of-range persisted schedules are discarded rather than trusted.

Latest attempt readback exposes ID, started/completed times and `Running`, `Succeeded`, `Failed`, `TimedOut`, `Cancelled`, `Superseded` or `Interrupted`. Only the latest attempt per current feed definition is retained. Older IDs return a specific not-retained error. A duplicate/manual trigger during an active operation or before the durable next-due time returns current attempt state and does not fetch again. Once due, a new trigger is a new operation; this is not an unlimited client idempotency-key ledger. The internal manual refresh method can explicitly bypass due time for owned validation; the HTTP refresh endpoint honors scheduling.

After an interrupted process, a Running reservation becomes Interrupted unless a validated persisted snapshot has the same generation/attempt ID. That snapshot is the authoritative success receipt even if the process exited before saving terminal status. Completed time may remain unknown in this recovery case. A committed snapshot is not subsequently reported as cancelled merely because the client disconnected or shutdown started. The last-known due reservation remains conservative if saving terminal status fails. Before calculating the next attempt, the scheduler uses the same committed receipt as health readback: a matching current feed/configuration/source and snapshot generation resets prior failure history. This preserves the retained due time, while the first subsequent failure starts at count one and the base interval. Succeeded means the complete snapshot committed; `attemptCompletedAt` may remain null until the separate terminal status write, and clients requiring that write must wait for the matching attempt and persisted timestamp.

## API and commit boundaries

Existing policy get/set/history/rollback API authorization remains intact. New routes:

- `POST /api/security/feeds/refresh`: `feedId`, current policy `revision`, current `snapshotRevision`. Requires Settings Modify and Administration Modify. Response contains current/latest attempt and snapshot token. A duplicate may return Running; poll the attempt endpoint for its terminal outcome. The endpoint revalidates the current session, privileges, primary role, policy revision and source/epoch after awaits and before durable activation.
- `GET|POST /api/security/feeds/attempt`: `attemptId`. Requires Settings View and Administration View. Missing/older attempts are not fabricated.
- `POST /api/security/feeds/cancel`: `attemptId`. Requires Settings Modify and Administration Modify. The response acknowledges a cancellation request, not terminal completion. Poll readback. A missing/completed attempt cannot be cancelled.
- `POST /api/security/feeds/rollback`: current policy `revision`, current `snapshotRevision` and a retained complete snapshot. Requires Settings Modify and Administration Modify, checked again immediately before commit. Small requests can use a `snapshot` form field. For snapshots up to 16 MiB, send `application/json` with the snapshot array as the body and revision/token in the query, authenticated through the Authorization header. The ordinary form reader's smaller limit still applies to form encoding.

`GET /api/security/policy/get` returns the current `snapshotRevision` token with health. Existing authenticated configuration backups contain the snapshot array. There is no new public cache dump or automatic history store. Keep a private validated backup to select a prior snapshot for rollback. Credentials are never in that array.

Fetch, strict decode, complete parse, normalization and index construction precede atomic file replacement. The complete multi-source cache is written/flushed to a unique temporary file, atomically renamed over the cache, then activated in memory. The cache replacement is a per-process whole-store transaction, although a normal refresh changes one feed and preserves the other configured feeds. Disk commit is the point of no return: process exit before rename retains the prior generation; exit after rename cold-loads the new complete generation. Schedule status is a separate atomic file and reconciles through the snapshot generation. These files are not claimed to be one cross-file transaction. Storage hardware/power-loss guarantees beyond flush/rename are not qualified.

Content SHA-256 covers canonical serialized feed ID/type/source URL/fetch time/expiry/sorted values/format/origin/source-configuration/provenance/validation time. It excludes the activation generation so rollback can create a new generation for the same validated content. The whole-store revision hashes serialized snapshots including generations, and changes on explicit restore. A checksum detects corruption; it is not publisher authentication. Native HTTPS uses platform certificate validation; synthetic TLS tests trust only their own generated certificate in their client handler.

Explicit rollback requires a nonempty integrity-checked snapshot array, exact current revision/token and matching configured sources. It restores the whole retained array, rather than selecting an individual feed. It assigns new generations and invalidates in-flight work. A stale/replayed token, incompatible source, checksum failure, revoked authorization or failed persistence leaves the current active generation unchanged. Expired/restored evidence remains inactive. There is no automatic rollback to an older generation and no activation of legacy unchecked backups through this new rollback endpoint. Existing legacy configuration-restore behavior remains separately available.

## Local validation and limits

Focused flags in `tests/Ipam.Tests`: `--feed-native-boundaries`, `--feed-reconciliation`, `--feed-management`, `--feed-durability`, `--feed-compatibility`, `--feed-native`, `--feed-timeout` and existing `--edl`. Native checks use generated pinned loopback TLS feeds, isolated native service/configuration roots, dynamic loopback HTTP/DNS ports, no DHCP scopes, denied recursion, disabled update checks, and authoritative synthetic names. They verify scheduled refresh, native rights/revisions/cancel/rollback/readback, Monitor evidence consumption and unchanged answers. Native service reload here means disposal/recreation of `DnsWebService` in the same process; it is distinct from the six real store-only child-process exits. Store checks separately use an injected transport and explicit process-exit checkpoints; they do not substitute for native transport tests. The separate native-boundaries fixture exits complete native service processes with owned exit code 73 and starts new OS processes over the same configuration, then verifies fresh authentication/modify privileges, exact attempt/generation/due readback, Monitor consumption, unchanged authoritative answers and no duplicate fetch. It also disconnects a real TLS HTTP request after the native snapshot commit, observes server RequestAborted, then verifies the same Succeeded receipt and no refetch on retry before due. Only that request uses an explicit clock seam to reach the existing due time; transport, native API, current authorization and commit code remain real. A stale retry token is refused; readback supplies the current token for the successful no-refetch retry. A raw JSON rollback of approximately 6.44 MB (the exact final byte count is recorded in its log) uses four disabled synthetic URL sources with 2,000 entries each, each source's corresponding text below 2 MiB. It verifies native commit, exact disk hash, separate-process cold validation, ordinary 16,777,217-byte refusal and an owned unavailable-destination write failure without changing the current generation. This qualifies that measured valid payload and the overlimit case, not every possible valid payload at exactly 16 MiB.

No UI assets are changed; desktop/390-pixel browser QA is not applicable to this API-only delivery. No production, live threat feed/MISP/model, external-recursion, multi-process/shared-store, multi-node exclusion, production availability, malicious-detection calibration or general RPZ interoperability result is claimed. Independent acceptance and any future integrated release remain separate gates.
