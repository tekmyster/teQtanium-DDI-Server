# DHCP synchronization implementation and target design

DHCP configuration and lease state must synchronize across clusters of three or more DDI servers alongside DNS. The protocol and management model must support a configurable number of nodes, rather than a fixed failover pair. Operators should see one managed service with per node applied revisions, replication lag, and health. Allocation ownership requires stronger coordination than periodically copying DNS configuration.

## Target cluster topology

An opt-in bounded voting log and learner/joint voter-transition API now has a separate [implementation contract](CLUSTER-VOTING.md). Its operator-driven coordination does not establish automatic takeover, complete production Raft, dynamic enrollment or production partition qualification. The broader topology below remains the target; existing allocation ownership is independent of quorum availability.

Separate cluster membership, voting membership, replicated state, and permission to serve DHCP. Every enrolled node receives the shared configuration and, by default, the committed lease state for all cluster scopes. A node can retain synchronized state without being assigned to serve a particular site. Future selective replication requires an explicit scope replica group and recovery contract; it must not silently weaken this default.

Use a consensus group with three or five voting nodes initially, plus additional nonvoting replicas when more service nodes are needed. Both voters and nonvoting replicas can be DHCP service nodes if their scope assignment and current ownership permit it. Nonvoting replicas receive the committed journal and snapshots, but their acknowledgements do not count toward quorum. The cluster leader coordinates state changes; it does not need to receive client DHCP broadcasts directly.

| Voting nodes | Majority required | Unavailable voters tolerated while a majority remains connected |
| --- | --- | --- |
| 3 | 2 | 1 |
| 5 | 3 | 2 |

These counts describe coordination availability, not client service reachability. A working quorum cannot replace a missing relay route or an unreachable serving node. Additional nonvoting replicas increase placement options without increasing voting fault tolerance. An even number of voters is supported by majority rules, but odd counts avoid an extra voter without a corresponding increase in failure tolerance.

Membership changes use a consensus protocol with safe configuration transitions, such as joint consensus. Add new nodes as learners, complete snapshot and journal catchup, then promote voters through the committed membership process. Removal or replacement of a voter must not create disjoint majorities. Do not implement membership by independently editing node lists on each server.

## Current implementation

`DistributedAllocation` and the actual `Scope` offer/commit/release paths now implement the first allocation protocol. New plans use `interleaved-v1`: stable, sorted owner identities select ascending eligible ranks directly (three owners: 1,4,7...; 2,5,8...; 3,6,9...). A missing algorithm field retains the legacy affine map so upgrading never reassigns persisted authority. Unknown algorithms are rejected. Exclusions are merged arithmetically; even a full IPv4 range need not be materialized. Configured reservations have deterministic individual ownership and are excluded from dynamic sequences, including reservation-only pools. Offers are durably held for the existing sixty-second offer window; full lease lifetimes are persisted before ACK. Outstanding offers recover after restart. A client selecting another server releases the unused offer and suppresses that transaction's delayed offers. Mutations carry per-owner sequences and before/after lease history, retaining the last 2000 changes per scope and owner.

Each store holds an exclusive process file lock. A separate flushed `dhcp-allocation.json.required` watermark binds the local node, immutable plan, sequence and content hash. It is written before snapshot replacement, so an interrupted write or an older snapshot cannot silently resume allocation. Preserve this watermark with the node's allocation state during offline recovery. Missing state/watermarks and conflicting or newer peer evidence stop service. Copying a whole old node directory to another active machine remains outside this protection: distinct physical servers must have distinct enrolled identities, and recovery must fence the old instance. A live restore never blindly replaces local authoritative allocation state with a replica.

Ordinary bootstrap requires disabled scopes with no active leases, offers or durable native protections. Reviewed live bootstrap also supports active native bindings while every scope is paused. It preserves the client, hardware address, hostname and latest acknowledged expiry, including conservative evidence from disabled peers. Where the balanced sequence assigns a protected address elsewhere, its formula owner permanently grants it to the native source. Initial ownership is prepared durably on every enrolled owner before the coordinator commits. Missing scopes are created only by the ordinary disabled, lease-free workflow. Ownership maps, ranges, exclusions and reservations cannot be changed in place. Scope drift withholds service. The existing cluster transfer still passes `scopes: false`; `dhcp-allocation.json` is separate from legacy scope files and participates in DNS-settings backup/restore and configuration transfer. Replication workers exchange bounded snapshots directly with all enrolled peers over HTTPS every five seconds and retry after failed links. Receivers use owner sequences to reject conflicting versions and ignore older snapshots; they do not replay an older full snapshot over newer authoritative state.

Compatible native lease and offer evidence retains the maximum protected expiry; a passive offer never replaces an acknowledged lease's state or identity. Direct protection updates and offer capture use the same merge rule. Captured offers preserve quarantine, and incompatible client or hardware evidence rejects the complete batch before persistence. An interrupted capture with a failed native scope save can therefore recover the latest acknowledged lifetime from the durable allocation barrier even when the scope file is older. Explicit native release and DECLINE operations retain their separate lifecycle semantics.

### Reviewed live ownership bootstrap

This is an administrator API workflow, not automatic failover. It currently requires the cluster primary as the native source and every enrolled, unfenced node as an owner. All owners must already have compatible scope ranges, masks, exclusions and reservations. Local listener enablement remains local. Source DHCP options become the shared policy; peer option differences must be reviewed before preparation. Do not enable two native servers or copy older leases over current authority.

1. Before pausing clients, obtain current configuration and lease-authority backups, preserve the original administrative session, and verify DNS availability. Use a separate fresh HTTPS administrator session on the primary. POST `/api/ddi/dhcp/migration/check` with `scope` to verify eligibility on all peers while native DHCP continues. Failure leaves native authority unchanged.
2. Pause the scope on every node, including dormant peers. Do not change options, enrollment or lease bindings during review. In-flight requests drain through UDP reply completion before capture. Native offers, ACK lifetimes and new DECLINE observations are durably protected before advertisement. Pre-upgrade offers and DECLINE history cannot be reconstructed: allow at least ten minutes after pausing an older implementation before capturing the migration, and retain its latest configuration/lease backups. This timing requirement is an operator prerequisite, not an automatically verified software gate. A disabled-scope flag alone does not prove that an older process released all DHCP sockets or drained its handlers; legacy concurrent listener factories can leave untracked receivers. If ingress or runtime drain cannot be verified, stop the switch and resume current native authority without restoring historical data. Any temporary DHCP-only ingress fence requires separate review and packet-level validation while DNS and administrative access remain available.
3. POST `/api/ddi/dhcp/migration/preview` with `scope`, a stable 32-hex `id` and optional `haGroups`. Save `response.state` privately. Review all source and disabled-peer native evidence, expiry times, protected offers/quarantines and resulting donor grants. Conflicting client/address evidence, out-of-pool live addresses and unknown offers reject the review. No ownership is installed by preview. Payloads are limited to 8 MiB.
4. Compute the uppercase SHA-256 of the UTF-8 JSON serialization of the returned migration using its camel-case property names and unchanged property/array order. POST `/api/ddi/dhcp/migration/prepare` with `migration` and `expectedHash`. Keep scopes paused. Each node compares current native evidence and configuration under its admission gate and persists the immutable initial authority before reopening admission. Prepared nodes reject serving, enablement and administrative edits. Preparation does not hold a scope gate across peer HTTP requests.
5. POST `/api/ddi/dhcp/migration/status` with `scope` to recover the saved `response.migration`, operation identity, hash, phase and acknowledged owners. After a timeout, dropped response or restart, retry preparation with that exact saved payload and hash. A retry never reseeds authority; it repairs interrupted shared-option application on a prepared node. Changed membership or a different payload rejects the operation. Never delete the journal or restore an older snapshot to force a retry. If an unprepared peer's evidence changed, keep all scopes paused and resolve the new protected evidence before retrying; there is no automatic abort/repartition API.
6. POST `/api/ddi/dhcp/migration/commit` with `scope`, the saved `id` and `expectedHash`. Every current owner must have acknowledged durable preparation. Peer commits precede the local coordinator commit. Partial commits and ambiguous responses remain recoverable with the same request. An unavailable peer is not permission to infer free addresses. Ordinary mesh traffic cannot import a new live plan or overwrite local preparation records. Preserve the safety-bound `.required` watermark with allocation state; missing, older or incomplete barriers withhold service.
7. Commit does not activate a listener. After independent manager QA and the deployment authorization gate, activate only the reviewed distributed serving roles through normal scope controls. Verify active client renewals and addresses, outstanding offers, quarantine, native options, concurrent allocations, replication, DNS service and fresh administrative read/modify access. Keep old administrative sessions until affected access paths pass fresh authentication and privilege checks. Report untested direct-broadcast, relay and management source paths separately.

Current validation includes three certificate-pinned HTTPS servers, parsed-wire requests with real UDP native ACK/capture and migrated-renewal replies, API edit/enable/delete/rename races, rejected scope restores, prepared-store restart, abrupt child-process termination at native/prepared/committed boundaries, actual lost prepare/commit responses, immutable replay, dormant peer evidence and old-state barriers. It does not establish production readiness, full-service power-loss testing, all source addresses, inbound broadcast/relay reachability, consensus membership changes or automatic takeover. Live migration has no new console screen; raw migration payloads are confined to this explicit administrator/developer API workflow.

After exhausting its own sequence, an owner uses previously granted addresses and then requests capacity from reachable donors. The donor checks its local leases/offers, durably holds the address, and returns its grant snapshot before the borrower can persist an offer. Donor grants do not expire autonomously and cannot be allocated by the donor after restart. Grant return and capacity reclamation remain unimplemented; repeated lost responses can consume capacity conservatively. New borrowing needs donor contact, while existing grants remain usable during isolation.

### Unused capacity from an unavailable owner

The offer path publishes `overflowRequestedUtc` only after an actual client request exhausts its unchanged own sequence and previously granted capacity. An external controller can then recover the failed owner's unused dynamic addresses. This is separate from lease-preserving failover: active leases, offers, DECLINE quarantine, static reservations and existing grants are not divided or overwritten.

With the owner externally fenced and its service stopped, run `DnsServerApp --dhcp-recover-unused ORIGINAL_STORE OWNER SCOPE RECEIVER1,RECEIVER2 RECOVERY_ID EXPECTED_SEQUENCE OUTPUT_JSON`. Use the original owner's watermark-bound journal, a stable 32-hex recovery ID, its reviewed current sequence, and an export path separate from the journal and its barriers. The store's exclusive writer lock rejects a running server. A receiver's replica is not a substitute for the original disk. Missing, stale or corrupt authority blocks recovery.

Eligible unused addresses are sorted numerically and divided round robin among sorted configured receivers. The original owner list and its interleaved sequences do not change. The complete division and permanent grants are persisted atomically in the original owner's replica and bound by its existing watermark. The same recovery ID retries the original division; changed receivers are rejected. An empty division also has a durable retry record. Each operation is bounded to 65,536 unused addresses and each owner/scope to 256 operations. Reservations remain with their original owner. Released or expired dynamic entries may become unused capacity; active entries remain protected.

On each selected survivor, POST `/api/ddi/dhcp/recoverUnusedOwner` with `owner`, `scope`, `recoveryId`, and the exported `state`. This requires a direct HTTPS administrator session with DHCP Modify and Administration Delete privileges. Cluster service tokens and proxied sessions cannot authorize it. The endpoint imports only the original donor's replica into the current scope state. It rejects an older donor journal, conflicting epochs or divisions, and any newer snapshot that drops permanent grants or saved recovery operations. Survivors continue to exhaust their own available sequence before using these grants. A recovery arriving during a failed donor call can satisfy the current offer.

### Controller delivery boundary

`scripts/recover-unused-dhcp-vmware.ps1` is safety-quarantined in the latest accepted local source. The quarantine refuses unqualified guest recovery, preserves journals/fences on uncertain outcomes and does not deliver usable automatic recovery. It is undeployed; automation remains Disabled. Do not enable it, launch guest recovery or change authority based on this guide. Original-journal command and receiver-import semantics above are separate from controller orchestration acceptance.

Historical bounded unused-capacity tests exercised the original journal, receiver import and unchanged-owner allocation behavior. They do not qualify the current controller after timeout/lost-response/exact-identity failures. Complete fail/timeout/lost-response/rejoin handling, noninteractive execution, affected-source fresh administrative access and actual client/relay behavior require independent acceptance before any separately authorized activation. Private node identities, credentials, deployment inventories and packet evidence must remain outside public history and CI. Lease-preserving takeover is a different workflow; see [historical Hyper-V limits](HYPERV-FAILOVER.md) and [dated status](DEPLOYMENT-STATUS.md).

Optional ordered HA pairs define local primary, local secondary and then regional recovery response preferences. The first primary adds no delay, its secondary adds 500 ms, and subsequent pairs add 1500 ms per group position. Unpaired recovery owners follow the configured pairs. Every serving node retains independent address ownership; a nonowner remains a replica. This provides preference and new-allocation continuity, not lease-preserving takeover of an unreachable owner's addresses. A server remains silent for DHCP REQUESTs concerning another owner's address rather than sending an incorrect NAK. Client DECLINE observations quarantine an owned address for ten minutes and can publish shared security context.

Planned connected-owner handoff transfers up to 256 explicit addresses in one durable write. POST `/api/ddi/dhcp/handoff` on the donor with `scope`, comma-separated IPv4 `addresses`, enrolled `receiver`, a stable 32-hex `requestId`, and the donor's reviewed `expectedSequence`. An ordinary user session with DHCP Modify permission is required; cluster service tokens cannot initiate handoff. The console offers selection of locally owned active leases, offers and declined addresses. Free addresses and existing reservations can also be selected through the API. This does not change the ownership formula or automatically move an entire scope.

The donor and its ACK path share the allocation lock. Surrender replaces each selected address with a permanent exclusive grant and preserves the previous client, hardware, hostname, state and expiry when active. The receiver cannot use an active surrendered lease or offer for a different client, and declined-address quarantine remains effective. Existing leases recover for renewal and retain at least their prior acknowledged lifetime. Shared DNS/security identity, historical lookup and IPAM lease observations include inherited leases before the receiver's first ACK. Released inherited leases retain a suppression record until the inherited lifetime ends; reclaim for another client remains conservative until then. Existing reservations retain their original client binding.

Surrender and delivery have separate outcomes: `receiverAcknowledged=false` means donor authority is already gone but the receiving node has not acknowledged persistence. Retry the identical request after connectivity returns; do not choose a new receiver or restore the old donor snapshot. The normal mesh also retries delivery. The operation is idempotent after a lost reply; a new operation against a changed donor sequence requires fresh review. Both donor and receiver preserve these protections after restart. Grant return, further forwarding, whole-scope drain orchestration and unreachable-owner takeover remain future work.

The controller exposes `/api/ddi/dhcp/state/get`, POST `/plan/set`, POST `/prepare`, POST `/state/ingest`, POST `/grant`, POST `/handoff`, and `/history/lookup` under the same prefix. User operations use DHCP permissions. Preparation, ingestion and capacity grants require direct HTTPS cluster sessions; proxied user sessions cannot mutate replication state. Snapshot payloads are capped at 8 MiB. The existing shared cluster token trusts enrolled members; cryptographic per-node attribution is still required for stronger member isolation.

`--dhcp` tests exercise the real offer, ACK, overflow and nonowner request paths, three-owner partitions, restart, stale snapshots, durable watermarks, process exclusion, historical attribution and planned handoff. Handoff checks include atomic batch rejection, old-owner ACK rejection, inherited release/decline before the first receiver ACK, reservation binding, lease-lifetime preservation, retry and restart. `--transport` starts three isolated servers and exchanges state through actual HTTPS endpoints using pinned lab certificates; it tests bootstrap, link failure, reconnect, grants, handoff delivery failure/retry, old-owner DNS cleanup and fresh-session privileges. Membership is seeded by the fixture. It does not validate upstream enrollment/DANE, physical fencing, an end-to-end DHCP relay or broadcast deployment, regional WAN behavior, clock jumps, full-directory clones, or production throughput.

For an isolated console lab, run the tests with `--transport --serve`. The fixture writes temporary connection details to `tests/Ipam.Tests/bin/Release/net10.0/lab-connection.json`; create the adjacent `.stop` file to terminate it gracefully. Original sessions remain open through fresh-session checks, and temporary service tokens and connection details are removed during cleanup. Browser validation exercised empty selection, review/back, successful handoff, readable inherited lease counts and desktop/narrow component layouts. The upstream application's surrounding shell still has its legacy minimum width; the shared-DHCP component is constrained to the narrow viewport with locally scrolling tables.

The primary continuously publishes content-hashed, revisioned scope option snapshots, and replicas reconcile those options while retaining local listener enablement and interface selection. The snapshots exclude active leases. Node-local DNS address selection is recomputed when the shared policy says to use that node as the resolver. Local option drift is reconciled even at the same desired revision. Configuration that would change allocation eligibility is rejected rather than shifting existing ownership. Reachable secondary peers still exchange lease observations when the configuration primary is unavailable. Renewals retain at least the previously acknowledged allocation lifetime when configuration shortens the new lease duration, protecting clients that might miss the renewal ACK.

Remaining work includes reservation/range migration, consensus membership and ownership changes, safe grant return, automatic lease-preserving failover and DHCPv6. Snapshot JSON rewrites and bounded history are an initial implementation rather than enterprise transactional storage. Fencing integration must be selected before automatic takeover is enabled. Static infrastructure addresses must be explicitly excluded from managed dynamic pools; discovery is not a substitute for those exclusions.

The sections below describe the target protocol beyond this first immutable-ownership implementation. Management API operations that change reservations, lease type, exclusions or membership still need the migration protocol; changing those values locally is not a supported distributed reconfiguration workflow.

## Replicated configuration

Replicate scope identity, network view and site, address ranges, subnet masks, exclusions, reservations, lease duration, DHCP options, and DNS update policy. Keep interface selection, listener addresses, server identity, and allocation role local to the destination node.

Each publication carries a monotonically increasing revision and content hash. Validate a revision before activation, apply it atomically, and acknowledge its status. A standby must not start serving simply because the primary scope is enabled. Deleting or renaming a scope needs a replicated tombstone or stable identifier so an offline node cannot resurrect obsolete configuration.

## Replicated allocation state

The preferred allocation mode uses exclusive address partitions and local durable journals. An owner can continue allocating and renewing within its partition when replication is interrupted, provided it retains its authoritative local state. Configuration publication and ownership changes use cluster coordination; individual leases do not require a WAN round trip. A node that loses its local allocation journal cannot infer availability from an older replica and must recover before serving.

Define durable events for offers or allocation holds, commits, renewals, releases, declines, expiration, reservation changes, and administrative removals. Include scope identity, network view, allocation epoch, sequence number, client identifier, hardware address, IP, hostname, event time, and absolute lease expiry where applicable.

Use a persisted journal and acknowledgements. Consumers must tolerate duplicate delivery, detect missing sequences, and reject updates from obsolete allocation epochs. Snapshot transfer includes its journal watermark; replay only subsequent events. Recovery must be resumable and detect corrupt or incomplete snapshots.

Persist offers and lease mutations locally before advertising or acknowledging them, then replicate the journal to peers. The management interface must distinguish locally durable state from peer acknowledged state. Delayed replication is safe for independent allocations because partitions do not overlap; it does not authorize takeover of a partition whose latest lease state is unknown. A future shared pool mode would instead require a consensus commitment for each allocation and renewal before acknowledgement.

## Automatic balanced allocation sequences

For each subnet, count the explicitly assigned allocation owners, not every cluster replica and not the servers currently reachable. Local HA members and regional recovery servers may participate according to the subnet policy. A recovery server that must allocate independently during isolation needs its own exclusive partition; a replica without a partition remains standby until safe ownership transfer.

Build an ordered list `P` of eligible dynamic addresses after removing exclusions, infrastructure addresses, and reservations. Let `A` be its length, `N` the configured number of allocation owners, and `s` the owner's zero based index after sorting by stable node identity. Generate candidates with `IP(s, k) = P[s + k * N]`, using nonnegative values of `k` for which `s + k * N < A`. The algorithm and configured owners are immutable parts of the plan. These disjoint ascending sequences differ in size by at most one. A peer outage does not change `N` or the owner indices. Reject zero owners and more allocation owners than eligible addresses.

For 100 eligible addresses and three owners, input sequences are `0, 3, 6, ...`, `1, 4, 7, ...`, and `2, 5, 8, ...`, containing 34, 33, and 33 addresses. These ranks refer to the eligible list after exclusions and reservations are removed. Reservations have separate explicit ownership and never enter the dynamic candidate sequences.

A server must exhaust available candidates in its own sequence before requesting capacity from another sequence. An unavailable peer is not evidence that its addresses are free. Overflow requires an atomic coordinated claim that accounts for the original owner's authoritative leases and outstanding offers. The original owner must durably hold the address and acknowledge that it will not allocate it before the borrower receives authority to offer or lease it. Commit and persist a unique grant identifying the address, donor, borrower, and ownership revision. Missing acknowledgements or ambiguous outcomes keep the address unavailable until recovery resolves the claim.

After a grant, both owner and borrower exclude the address from independent candidate selection; only the borrower can serve its granted lease. Persist grants across restart and replicate them to all nodes. Returning an address to its original sequence requires a coordinated release and protection of outstanding leases; a local grant timer must not make an address reusable while a borrower can still renew it. A borrower may continue serving a previously granted address during disconnection according to its persisted authority. It cannot obtain new overflow grants while the required coordination is unavailable.

Persist and replicate the resulting ownership map with a revision. Disconnected nodes continue using the same map. A failed heartbeat never reduces `N` or triggers autonomous repartitioning. Adding or removing an allocation owner generates a proposed balanced map, but activates changed addresses only after a safe handoff. Existing leases and offers remain protected while the old owner drains or transfers its state. Temporary imbalance during migration is preferable to duplicate leases.

Changing pool ranges, exclusions, or reservations also requires this migration procedure when ownership or address eligibility changes. Replacing the ordered eligible address list independently on each node would otherwise shift boundaries and create overlap. When a former owner cannot be reached, fence it and recover authoritative state or wait a conservatively bounded outstanding lease lifetime before reusing its addresses. The lease lifetime bound must account for renewals and offers made during isolation, not just the last replicated expiry.

## Ownership and failover

Allow multiple allocation owners per scope, each with an exclusive address partition, plus synchronized standby nodes. Organize service nodes into local HA groups with primary and secondary preference and ordered regional recovery targets. Serving preference determines who normally responds; partition ownership determines which addresses a node can allocate safely. Prefer explicit scope placement and ownership to assumptions based on DNS primary or secondary roles.

Partition ownership revisions must be committed through cluster coordination. A committed revision alone cannot revoke an isolated server's old map while that server is permitted to continue operating locally. Ownership transfer therefore also requires confirmed relinquishment or external fencing of the former owner, plus protection of its outstanding leases. Validate each local allocation against the active map and durable lease journal. Heartbeats or a newly elected coordinator alone cannot authorize reuse of another owner's partition.

Automatic takeover, if selected, requires coordinated ownership transfer, fencing or confirmed relinquishment, and validated lease recovery. During a link failure, each node may continue using its own partition, but no node can claim another partition based on silence. A minority partition cannot publish a new ownership map. DNS continues resolving using local configuration. Forced disaster recovery without a majority is a separate procedure requiring isolation of the old owners and conservative treatment of outstanding leases.

A recovering node first joins as standby, catches up its snapshot and journal, and proves it has the current allocation epoch before becoming eligible to serve. An outdated node must not reactivate scopes automatically after restart. Ownership transfer must account for outstanding offers and the latest committed lease expiries.

DHCP renew, rebind, DHCP server identifier, relay routing, direct broadcast reachability, and DNS update ownership need an explicit deployment design. Decide whether takeover preserves a service address or relies on client rebind behavior. Test both relayed and directly connected clients when both paths are supported.

## Management and security

Authenticate replication through node identities and encrypt transport. Apply dedicated replication permissions and validate messages independently of transport authentication. Replay protection uses scope epoch and sequence state stored durably. Bound journal retention, snapshot size, replay work, and replication queues.

Show desired and applied configuration revisions, last durable lease sequence, acknowledgement lag, active owner, ownership epoch, voter and replica roles, quorum health, and recovery progress for every node. Audit policy changes and ownership transfers. If enrollment or integration requires ACL or credential changes, retain the original administrative session until a fresh session verifies authentication, privileges, and required authorized paths.

## Acceptance requirements

1. A scope, option, reservation, exclusion, rename, and deletion appear consistently on every assigned node, while local listener settings remain correct.
2. Offers, commits, renewals, releases, declines, expirations, and administrative changes survive owner restart and converge after peer reconnect.
3. Duplicate, out of order, and missing events cannot resurrect a released lease or allocate an already assigned address.
4. Concurrent clients receive distinct addresses during normal operation, takeover, and recovery. Outstanding offers participate in this check.
5. A network partition never allows conflicting allocations for the same scope. Test three voters split 2 to 1 and five voters split 3 to 2; isolated owners can allocate only within their unchanged exclusive partitions and cannot publish new ownership.
6. A stale or partially restored node cannot serve until its role and state are validated. Disk full, journal corruption, and interrupted snapshots produce explicit degraded health.
7. Direct and relayed DHCP discover, request, renew, and rebind flows work under the supported ownership model; associated DNS updates remain consistent.
8. Replication lag, lease latency, allocation throughput, and event loss are measured. Lease acknowledgement proves local durability; peer acknowledgement and lag are reported separately.
9. Existing standalone DHCP behavior remains compatible when replication is disabled.
10. Run synchronization tests with three and five servers and with five voters plus additional nonvoting replicas. Every replica converges after disconnect and reconnect; node counts are configuration rather than hardcoded pairs.
11. Add, promote, replace, and remove nodes while lease traffic continues. Replayed membership messages cannot create independent voting majorities or reactivate an obsolete owner.
12. A three voter cluster can coordinate changes with one unavailable voter and a five voter cluster with two, provided the remaining majority is connected. Loss of majority prevents ownership changes but does not stop healthy owners serving their established partitions.
13. Run multiple owners within one scope and across different scopes. Moving a partition does not duplicate an address or alter ownership of unrelated partitions; voter and nonvoting service nodes enforce the same address ownership rules.
14. For varying pool sizes and owner counts, all eligible addresses have exactly one owner and partition sizes differ by at most one. Include exclusions, reservations, uneven division, and invalid owner counts.
15. Drop every replication message while owners allocate and renew concurrently. No owner issues an address from another owner's partition. Restore communication and verify journal convergence.
16. Change allocation membership while a former owner is disconnected. The proposed map cannot activate overlapping ownership until that owner is fenced and outstanding leases are protected.
17. Verify that overflow begins only after the owner's sequence has no available addresses. Race multiple borrowers against the original owner for the same candidate; at most one allocation authority succeeds. Drop messages and restart participants at every grant stage to verify durable holds, safe recovery, and eventual convergence.

## Delivery boundary

This design establishes the required behavior. Runtime replication, durable journaling and stable ownership enforcement are implemented in the bounded forms above. Safe consensus/membership changes, live ownership edits, grant return, DHCPv6 and working production recovery remain incomplete. The latest parser/transport repair is locally accepted and undeployed; the actual live causal exception remains inferred. Scope backup, source tests and a successful build do not satisfy production acceptance.
